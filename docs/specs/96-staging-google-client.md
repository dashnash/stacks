# #96 Give staging its own Google OAuth client (SEC-05)

Both environments in `stacks.config.json` use the same `googleClientId`, and the platform accepts
any Google ID token with that audience (`platform/api/src/google.ts`). A credential captured on a
staging page is therefore valid on production for about an hour. Staging gets its own client, and a
test makes sure the two never match again.

## Decisions (settled, don't reopen)

| Topic | Decision |
| --- | --- |
| The id | The owner creates the client and gives the agent its id (client ids are not secret). The agent writes the check first; the PR isn't ready until the id is in `stacks.config.json`. |
| iOS staging app | Found while implementing: the staging iOS build embeds the web client id as `GIDServerClientID` (`native/ios/Config/Staging.xcconfig`, generated by `scripts/ios-xcconfig.mjs`). Regenerate it with the new id in the same PR; the staging TestFlight build must be rebuilt (the `iOS` workflow) after merge, or native sign-in on the old staging build fails with "unknown app". The new web client must live in the **same Google Cloud project** as the staging iOS client (`880697273676-…`), or Google won't issue tokens addressed to it from that iOS client. |
| Check | A Vitest test in `packages/infra/tests/config.test.ts` (default location) loads the real `stacks.config.json` and asserts: the staging and production `googleClientId` differ, and no web client id of one environment appears in the other's `native.googleIosClientIds`. |
| iOS clients | Already one per environment; unchanged. |
| Sessions | Existing staging sessions stay valid (they're platform sessions, not Google tokens); people re-sign-in to staging only when their session ends (default). |

## Manual steps for the owner (before the PR merges)

1. Google Cloud Console, **project 880697273676** (the one holding both iOS clients) → APIs & Services → Credentials → Create OAuth client ID → Web application,
   name "Stacks staging". Authorized JavaScript origins: `https://auth.test.dashnash.ninja`
   (and `http://localhost:5173` only if you use it for local sign-in). No redirect URIs are needed
   (the portal uses Google Identity Services' ID-token flow).
2. Give the agent the client id (ends in `.apps.googleusercontent.com`).
3. After merge and deploy: sign in at `https://auth.test.dashnash.ninja`, and check that production sign-in still works.
4. Rebuild the staging iOS app (run the `iOS` workflow for staging) so it asks Google for tokens addressed to the new client; until then native sign-in in the old staging build is rejected.
5. Optional: in the production client, remove any `test.` origins left over.

## Changes

- `stacks.config.json`: staging `googleClientId` → the new id.
- `native/ios/Config/Staging.xcconfig`: regenerated with `node scripts/ios-xcconfig.mjs`.
- New test as above.
- `docs/SETUP.md` §1b: note the check enforces one client per environment.
